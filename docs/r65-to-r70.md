# Upgrade a managed r65 installation to r70

This procedure is for a host whose active release is
`/opt/trop/releases/r65-20260918` and whose deployment config is in
`/etc/trop`. Run it **on that Ubuntu host**. It uses the current public
`trop-bootstrap` launcher because the `trop` bundled with r65 predates
`trop upgrade --release`. The target release's installer performs the update.

It does not change hostnames or move a custom/home-directory installation into
the managed layout. Those cases need separate review.

The r65 release package has a known fresh-install defect: the `trop-media`
Helm chart can leave the Alpine CA-certificates image digest placeholder
unexpanded. This affects even the Server-only profile. It prevents a clean
r65 installation from becoming the healthy starting point required below.
If the r65 deploy never completed, resolve that installation first; an r70
upgrade command is not a substitute for diagnosing a partial deployment.

## 1. Check the starting point

```bash
readlink -f /opt/trop/current
sudo test -f /etc/trop/zarf-config.yaml || \
  sudo test -f /etc/trop/zarf-config.enc.yaml
trop health
```

Expect the first command to print
`/opt/trop/releases/r65-20260918`. If `current` is absent, points outside
`/opt/trop/releases`, or the host is degraded, stop and investigate its
installation state. Do not use this procedure to guess at a partial migration.
Keep a host/data backup according to your site's normal policy. The following
additional backup protects the private deployment config:

```bash
sudo install -d -m 0700 /root/trop-backups
sudo cp -a /etc/trop /root/trop-backups/etc-trop-before-r70
```

That directory contains credentials and signing material. Keep it root-only
and do not attach it to a ticket or paste it into chat.

## 2. Download the current launcher

The example pins the public v0.4.2 launcher and checks its published SHA-256.
The directory `~/trop-bootstrap` holds only the launcher; TROP stays under
`/opt/trop`.

```bash
mkdir -p "$HOME/trop-bootstrap" && cd "$HOME/trop-bootstrap"
curl -fL https://github.com/defencebay/trop-bootstrap/releases/download/v0.4.2/trop-bootstrap \
  -o trop-bootstrap
printf '%s\n' '3849015cd166d58fb73b07dabf54d8ac2813ba887c637d5a7e3da461f0026638  trop-bootstrap' \
  | sha256sum -c -
chmod +x trop-bootstrap
```

## 3. Select r70 and update

```bash
./trop-bootstrap --release r70-20260924
```

Paste the TROP token at the **hidden** prompt. Keep the recommended
`/opt/trop/releases/r70-20260924` destination and choose to install after
download. Bootstrap verifies the signed release packages, detects the active
r65 installation, reuses `/etc/trop`, and calls the r70 installer in
`update` mode. It does not rerun setup or regenerate the deployment secrets.
Do not add `--dest` here; a managed upgrade must use the managed destination.

For a deliberate pause after download, use:

```bash
./trop-bootstrap --release r70-20260924 --fetch-only
cd /opt/trop/releases/r70-20260924
sudo ./trop-install.sh update zarf-package-trop-platform-amd64-r70-20260924.tar.zst
```

The package name above is for amd64. On arm64, use the arm64 filename printed
by bootstrap. The token is still entered at a hidden prompt during fetch.

## 4. Validate before handing the host back

```bash
readlink -f /opt/trop/current
trop-doctor --version
trop status
trop health
trop-doctor install-validate
sudo cat /opt/trop/operation-state
```

Expect `current` to point to `/opt/trop/releases/r70-20260924`,
`trop-doctor` to report v0.4.5, and the operation state to end with
`status=succeeded`. `install-validate` prompts for administrator
credentials. Also open the URLs enabled by this host's profile from a client
that uses the site's DNS. A green local command alone does not prove that
client DNS and ingress are correct.

If deployment fails, `current` remains on the last release that passed its
health gate, but some Kubernetes workloads may already have changed. Inspect
`trop health` and the printed failed step before retrying; do not assume an
automatic data rollback. A second bootstrap attempt for the same target
revalidates its cached signed bundle.

## Does r65 need a migration script?

r65 and r70 both use the `trop-system-layout-v1` release contract. For a
healthy **managed** r65 host with config in `/etc/trop`, no directory or
config-format conversion is required: the r70 installer consumes the existing
config during `update`. New optional host-integration flags missing from an
older config stay `false`; an update does not silently opt in. This layout
compatibility does not repair a failed r65 deployment or migrate application
data from a different installation scheme.

An isolated Server-only r65 → r70 test on 2026-09-25 passed the r70 update,
health gate, `trop status`, `trop health`, and `trop-doctor install-validate`.
The r65 test fixture needed a manual repair of the image placeholder above
and activation after a transient enrollment TLS check, so this test does not
establish that a fresh r65 deployment completes unattended. Platform + TOC
was not covered by this release-to-release test.

An older home-directory installation is a different case. When its plaintext
config is still under the old release directory, use the launcher's
`--config /absolute/path/to/zarf-config.yaml` import path and review the
resulting setup plan. `--config` does not accept an encrypted config; place
the encrypted file under `/etc/trop/zarf-config.enc.yaml` with root-only
ownership and permissions before using the managed path. A degraded or
ambiguous host is downloaded but not automatically deployed.
